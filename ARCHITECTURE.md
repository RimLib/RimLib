# Architecture

## Ownership

```text
renderer components -> workflow hooks -> ModStoreApi
                                            |
                                    isolated preload bridge
                                            |
                                  validated Electron IPC
                                            |
                      application services -> platform adapters
                                            |
                                         VaultStore

shared domain types, validation and pure transformations
are available to both sides without platform dependencies
```

- `src/shared`: current mod/tag records, stored database validation/normalization, tag transformations, package matching, subscription safety helpers and the IPC contract. Tag creation/editing validates the latest vault and selected targets atomically, preserving unknown tag fields. Shared modules must not import React, Electron, Node or either process's implementation.
- `src/main`: filesystem, OS dialogs, logging, public Workshop HTTP requests, Steam SDK access, strict standalone mod-list XML import/export, guarded `ModsConfig.xml` reads/writes and serialized application operations. `index.ts` composes these services, owns the native window lifecycle and registers the allowlisted official-preview image protocol. The IPC handler checks the sender and main frame, validates arguments and applies the relevant Steam or game-state gate before an action.
- `src/preload`: exposes only `ModStoreApi` and diagnostics through `contextBridge`. Its invocation wrapper uses the shared channel/argument/result contract; no generic IPC transport is exposed to the renderer. Electron's untyped response assertion is confined to this adapter.
- `src/renderer/src/components`: store-connected feature components, pure presentation views, dialogs and shared controls. Connected panels select shared session state directly; their exported views remain stateless and easy to test. Components never import privileged APIs.
- `src/renderer/src/hooks`: orchestration, persistence scheduling, background status, selection and dialog workflows. `useSettingsDialog` owns path selection/access tests, `useTagDialogs` owns tag mutations/dialog transitions, and `useWorkshopActions` owns synchronization. `useDraftChanges` executes confirmed drafts and reports into the draft store, delegating the mutation sequence to `services/draftActions.ts`. `useModSelection` reconciles current displayed ordering with the workspace store. All durable mutations still use the single `useModVault` save/operation lock.
- `src/renderer/src/stores`: workspace and draft state in Zustand, scoped to one app mount. The workspace store owns transient search text/scope and sorting, focused mod, multi-selection and context-menu targets. The draft store owns per-mod subscription/activity intentions, the projected active order and its verified baseline, chronological reorder-operation metadata, review state, progress and its apply lock. It exposes a bounded, versioned intent snapshot that `useModVault` mirrors into device-local vault state; review/progress/apply-lock state stays transient. Neither store performs IPC, storage or Steam work directly.
- `src/renderer/src/services`: the native/browser store adapter, notifications, diagnostics, settings persistence, and optional user-owned Firebase client. The browser adapter preserves the Promise/error contract but uses separate local storage and cannot execute native actions. Firebase Authentication and Firestore run as unprivileged renderer clients with user-provided Web app configuration; no service-account credential crosses the preload bridge.
- `src/renderer/src/utils`: derived presentation views, filtering, ordering and selection logic. `activeMods.ts` and `library.ts` build one known-mod universe and partition it by active package IDs; `modSort.ts` proposes a deterministic dependency-aware order without performing I/O; `modListImport.ts` validates the preload result and resolves its ordered package IDs against known physical rows. `tagDialogs.ts` defines one explicit dialog state and its valid transitions. An editor retains its return state; a bulk chooser stays mounted underneath it to preserve checked tags and search. User tag mutations live in `shared/tags.ts`, not in a UI utility.

Lint enforces the process import boundaries, so they are not only conventions. There is deliberately no generic repository framework or dependency-injection container; tests use existing service constructors and narrow function parameters.

## Renderer State

[Zustand](https://github.com/pmndrs/zustand#using-zustand-without-react) manages shared, transient workspace interactions through a vanilla store and React selector bindings. `WorkspaceStoreProvider` creates a fresh store for each app mount; there is no module-global singleton or persistence middleware. Selectors return stable state references rather than freshly constructed objects. Panel view changes preserve the other panel's reference, and no-op actions do not notify subscribers.

Consumers receive observation methods and named actions, not raw `setState`. Selection, focus and context opening use the latest synchronous state and existing pure selection rules, avoiding parallel React-state/ref copies. Store-connected panels read their search/sort/filter state, selection and pending drafts directly, then delegate rendering to pure views; callers pass only domain data and workflow commands. Actions receive current displayed IDs rather than keeping a second mod collection. Reconciliation removes hidden targets and closes invalid menus in one transition. Tag searches derive their names from the current vault, so tag edits need no parallel workspace cleanup.

The shared library sorter defines unavailable metadata as either a missing/unusable package ID or a generated non-official active placeholder without an installed path. Its **Invalid first** mode groups those entries before complete entries. Active sorting consumes the unique invalid-ID set from the validator and preserves the projected game order within both groups; Library sorting preserves newest-first order. The Library-only **Not subscribed first** mode groups rows by their projected subscription state, then preserves newest-first order inside each group; Active does not expose that option. **Newest first**/**Oldest first** compare the maximum valid `addedAt`, `downloadedAt` and `steamUpdatedAt` timestamp, use the mod ID as a deterministic tie-breaker and deliberately exclude `metadataUpdatedAt`, which records a RimLib refresh rather than an installation/update event. Exact official Core/DLC identities remain valid even while optional installed details are loading.

`activeValidation.ts` is the pure Active diagnostics boundary. It evaluates the projected membership and order, so every activation, deactivation, manual move, Auto-sort and Undo is reflected before Apply. It emits typed per-mod findings for missing dependencies, incompatible declared game versions, violated metadata/dependency/bootstrap ordering, incomplete metadata, duplicate package IDs and cycles; the footer count is the unique affected-mod set. Version comparison uses parsed major/minor and skips absent/unparseable support data. The validator consumes the concrete constraints exposed by `modSort.ts`, avoiding false errors from the sorter's deterministic tie-breaking and ensuring Auto-sort fixes the same order relationships that validation reports. Diagnostics never mutate or block the draft; their optional repair kind routes through the existing dependency-activation or Auto-sort staging workflow.

The Active footer's mutually exclusive session filter combines validation and projected membership status. Invalid and pending-activation states filter Active; pending deactivation filters Library while its control remains in the Active footer. One atomic workspace action routes the selection to the appropriate panel and clears the other panel's status filter. Counts derive only from the draft's unique activity intentions, never from subscription, order or library-removal work, and the selection returns to Total when its final supporting intention is undone, discarded or applied.

Active drag-and-drop is enabled only when the panel shows the canonical **Load order**, has no search query and is not filtered to an Active subset. Rows expose a dedicated draggable grip; dropping computes a before/after move against the complete projected Active order rather than treating a presentation sort as game order. The Active-only **Move to position…** context action remains available from every presentation and accepts a one-based final position in that complete order, providing an exact and arbitrary-distance alternative to dragging. Neither path changes the selected display sort, clears a search or emits a virtual-list reveal request.

Once active configuration loading settles, initial workspace selection chooses the first projected Active row, falling back to Library only when Active is genuinely empty. It is a normal selection/focus update and never emits the virtual-list reveal request reserved for a row newly staged into Active. Steam/local source markers are image overlays anchored to the top-right instead of centered over the artwork.

A staged deactivation records a transient presentation priority against the exact current Library view. Matching rows are stable-prepended after ordinary filtering and sorting, so the latest deactivations are easy to find without changing the selected sort or issuing a scroll request. Any Library search, scope or sort change creates a new view and immediately restores normal ordering; undoing or reactivating a row prunes its stale priority. When installed metadata replaces a temporary row ID, activity intentions and this priority rebind only through one unambiguous normalized package-ID match; subscription and removal identities stay exact.

The vault remains the only durable source of mod records, tags, notes and device-local unapplied intent. RimWorld's configuration remains the authoritative durable source for applied active membership and order. `useModVault` still owns debounce, serialized saves, revision checks, operation locking and before-close flushing; Zustand never bypasses it. A successful installed-mod scan reconciles scanner-owned filesystem metadata and newly discovered non-official rows into the vault without pruning temporarily absent folders or replacing personal/cloud fields. Steam/active observations and destructive-action guards remain in their workflows and main-process services. Dialog forms, notifications, operation progress and presentation controls stay with their local owners. Reopening resets filters, focus, multi-selection and menus, restores the bounded pending-intent snapshot, and then revalidates it against current library/configuration state before Apply.

## Draft Workflow

Subscription changes, activity changes, load-order operations and library removals are device-local intentions. Their minimal, versioned identity/baseline snapshot is saved through the normal vault lifecycle and restored after restart; it deliberately excludes review UI, progress and full mod metadata. A mod can carry one net subscription intention and one net activity intention; opposite intentions in the same category cancel. Every successful manual drag or exact-position move appends a chronological, replayable reorder operation while updating the same projected final order. Auto-sort is a replacement boundary: it ignores the user-reordered projection, starts from authoritative order plus projected membership, removes all earlier reorder operations and records the concrete moves needed for its result. Manual moves after Auto-sort append after those operations. Every move captures the membership context in which its position was staged. Activity staging and undo retain that context instead of clearing or reinterpreting the operation; newly activated packages join the projection and pending deactivations remain in the hidden order template so undo restores their position. Staging validates a whole selection before changing it, and restore/Undo/Discard never contact Steam or write `ModsConfig.xml`; Discard also clears the saved reorder history. Projected active/inactive panels move rows immediately for activation/deactivation drafts. Activating an unsubscribed saved Workshop mod atomically stages subscription before activation; the same helper is used by direct row activation and dependency repair. Subscription drafts update status and available actions without otherwise deciding panel membership. The global inactive cleanup derives its complete target set from that projected panel, independent of search, and sends the same guarded unsubscribe intentions through the draft. Metadata refresh and tag edits remain immediate and preserve pending intentions.

Dependency repair resolves every missing normalized package ID against the complete projected Library, never the filtered view. It rejects an unavailable or ambiguous package before staging any target, then submits the resolved set through compound activation. Auto-sort uses a separate pre-proposal dependency plan: it aggregates missing packages across the projected Active list, follows each uniquely available match to include its own dependency chain, classifies exact Library matches as available and identifies unavailable or ambiguous entries, then presents those results in a decision modal. The user can cancel, sort the current membership, or atomically stage all available dependency activations/subscriptions before staging the expanded order. The first staged dependency becomes the focused Active row; a hiding Active search is cleared and the virtual list reveals the row so Mod Info immediately exposes any dependency problem of its own. Virtual-list reveal is an explicit, numbered, one-shot Active-panel request emitted only when a row is newly projected into Active. Global focus, startup fallback selection and manual reorder proposals never drive scrolling in either panel. Its compact staging notice is derived from the activation intentions and disappears as soon as any tracked activation is unstaged. This keeps the dependency warning, projected panels and apply order consistent while leaving discovery or download of absent dependencies to the user.

The footer opens a full review. Reorder rows are rendered from the captured operation history in chronological order; they explain how the projected order was produced but do not multiply configuration writes. Deletion additionally requires acknowledgement. Removing an inactive subscribed Workshop mod atomically stages both its unsubscribe and removal; a pending subscribe is cancelled instead of creating contradictory work. A pending removal keeps its projected row available to Mod Info, where **Add back** calls the category-specific undo for `remove`. That deliberately leaves a separately staged `unsubscribe` untouched. Subscribe, unsubscribe, removal and full inactive-cleanup controls never poll or gate on Steam, Workshop-folder presence or installed-metadata availability while staging, so the complete intention can be prepared offline. Applying captures and locks the queue, flushes personal edits through `useModVault`, checks Steam once when subscription work is present, reloads targets and validates destructive targets against authoritative subscription, installed-identity, active-configuration and saved-library state. It also validates requested active membership/order against the captured `ModsConfig.xml` baseline. An unavailable client, folder or unverifiable target produces an apply error and retains the unresolved draft, including its reorder history. Work executes in dependency-safe phases: subscribe first, write final active membership/order exactly once, unsubscribe third and remove saved records last. A successful configuration write clears the captured reorder history; a failed write retains it, and Discard clears it without I/O. This permits a single reviewed draft to subscribe before activation, deactivate before unsubscribe, or unsubscribe before library removal. Each native subscription action still rechecks its guards and binds the expected Workshop identity. Removals are reloaded/revalidated, checkpointed and committed only after external-state steps.

When that same canonical operation count is zero, the footer replaces its draft actions with **Run RimWorld**. The renderer takes the ordinary vault operation lock so pending personal edits are flushed, then invokes a no-argument main-process channel. The main process opens only the fixed `steam://rungameid/294100` URI; no path, URI or launch argument crosses from renderer input. Launching never writes `ModsConfig.xml`, applies a draft or clears pending work, and any OS protocol error returns through the normal action notification path.

The main-process active writer requires valid unique package IDs with Core exactly once, resolves a configured symlink to its canonical target, rejects a hard-linked live configuration, compares the live normalized order with the review baseline, verifies that RimWorld is closed, writes a sibling `.rimlib.bak`, then atomically replaces only the `activeMods` XML element. The hard-link check is repeated at the atomic publish boundary. Any mismatch fails closed. Execution reports named steps and per-step progress. Confirmed changes leave the queue only after their result is adopted; the first failure stops later work, while completed changes remain recorded and unresolved intentions remain available for review/retry. Closing without applying discards intentions only; tags, saved mods and previously applied external changes stay durable.

## Standalone Mod-List Files

Import and export are desktop-only `ModStoreApi` operations. The renderer supplies no input or
output path: the main process owns the native open/save dialogs, and the preload exposes only the
typed operations rather than generic filesystem or IPC access. The browser adapter rejects both
operations.

`main/modListFiles.ts` accepts a bounded UTF-8 RimWorld `ModsConfigData` document, rejects DTDs,
entities, unsupported structure and attributes, and validates the version, entry limits, unique
package IDs, expansion IDs and exactly one Core entry. The renderer then builds a preview by
resolving package IDs against the complete known inventory. Missing IDs remain visible and are
omitted only with explicit confirmation; duplicate physical copies use a stable selection policy,
including RimSort's `_steam` Workshop hint. A confirmed import requires a clean draft and stages
one atomic projected Active list against the current configuration baseline. It never writes the
game configuration directly.

Export serializes the renderer's projected Active list, so pending membership and order changes
are represented without being applied. Package IDs and registered DLC IDs are rendered lowercase.
The renderer derives RimSort's `_steam` Workshop-copy hint only from distinct copies in the current
installed-filesystem inventory, never from saved or stale library rows. Installed metadata enriches
import resolution and duplicate-copy hints but is not an availability gate for either standalone
file operation; saved rows and Active placeholders provide the degraded offline view. A failed read
may retain a previously verified in-memory configuration snapshot for standalone list preparation,
but never authorizes a game write: Apply still re-reads and compare-and-swap validates the live
configuration. The main process renders canonical XML with the retained/current game version and
then uses compare-and-swap atomic replacement. The export target is kept separate from the guarded
active writer: canonical-path and device/inode checks refuse the live `ModsConfig.xml` and its
symlink or hard-link aliases.

## Active Ordering

`steamWorkshop.ts` extracts base, version-keyed and force `loadBefore`/`loadAfter` declarations from installed `About.xml` metadata. Package IDs are normalized case-insensitively and duplicate declarations are collapsed within each list. Version-keyed groups retain their version so the pure sorter can replace the base list with the matching group for the version read from `ModsConfig.xml`; force rules remain unconditional and are appended. Declared dependencies use the same base-versus-version-override model.

`sortActiveMods` models applicable explicit rules and inferred dependency relationships as a directed graph. Explicit ordering wins over a directly reversed inferred dependency and emits a warning. Known early packages (Prepatcher, Harmony, Visual Exceptions, Core and official DLC) and their predecessor closure are topologically sorted as a first tier; the remaining graph is sorted second. RimLib prefers the fixed Prepatcher → Harmony → Visual Exceptions → Core → Royalty → Ideology → Biotech → Anomaly → Odyssey sequence, adding each preference edge only when the metadata graph has no reverse path. Thus explicit rules and dependencies win and preferred ordering cannot synthesize a cycle. At the same available level, early-tier prerequisites use package ID while ordinary nodes use normalized name, package ID and original index as stable tie-breakers. Missing targets and missing package IDs are non-fatal warnings; missing-ID rows stay at their original indexes. Duplicate active package IDs and cycles are structured failures that return no proposal.

Ordering is a proposal boundary, not an I/O boundary. Display sorting changes only row presentation; Auto-sort, drag-and-drop and exact-position moves are commands that propose a game order. The draft stores one projected final order and the original active baseline separately from its review history. Every successful manual move appends a stable chronological operation containing package identity, its before/after position and the active membership visible at staging time. Auto-sort computes from projected membership in authoritative order, deliberately ignoring pending manual ordering, then replaces the full prior reorder history with deterministic replayable moves; manual moves made later append after them. Activity changes keep that history and replay each move in its captured membership context, preventing a later activation or deactivation from changing an unrelated ordering relationship. Relative drops and exact positions operate on the complete projected order, and the active panel projects their result immediately; the exact-position modal is the accessible arbitrary-distance alternative when a target is outside the virtualized viewport. When the missing-dependency modal adds available matches, their subscription/activity intentions and the order covering the expanded membership are staged together. The review exposes Undo for every order operation. The review/apply path is the only route from any proposal to `ModsConfig.xml`, and it collapses all displayed reorder operations into one guarded write of the final projected order. Apply failure preserves the operation history, while a successful configuration write or Discard clears it. The algorithm is RimSort-inspired but intentionally does not claim RimSort's community rules database or incompatibility knowledge.

## Constants And Keys

`shared/domainConstants.ts` owns persisted sources, activity states and subscription actions. Types derive from these frozen maps, and runtime validation uses the same values. `shared/ipc.ts` owns invoke/event channels; the preload and main process reference those maps rather than repeating wire strings. Lint rejects raw protocol/action keys outside their owning modules.

`shared/storage.ts` owns stable database/browser storage names, and `shared/limits.ts` owns read deadlines, Steam import/cache policies and standalone mod-list size/entry limits. Logging policies remain in `shared/logging.ts`, native OS/error/window constants in `main/platformConstants.ts`, and renderer modes, filters, sorting and UI timings in `utils/uiConstants.ts`. Dialog transitions and tooltip placements stay with their respective workflow utilities. Database validation schemas are checked with `satisfies` against their domain field keys.

Supported IPC names, database filenames and schema version have explicit contracts. Retired invoke channels and subscription actions are rejected; they are not compatibility aliases. Tests deliberately keep independent literal fixtures to verify storage contracts. Use named constants for identifiers and policy decisions; ordinary labels, HTML/OS API vocabulary, arithmetic identities and presentation classes need not become a global constants catalogue.

## Data And Safety

The local v3 vault separates canonical `library` records from machine-specific `deviceState.steam`. Stored mods do not contain `subscribed`; the runtime derives membership from locally observed Workshop IDs plus explicit pending subscribe/unsubscribe actions. Optional Firebase sync mirrors only portable mod fields and personal tags into per-entity user documents; device paths, file sizes, download/subscription observations, settings and transient focus remain local. Firestore writes carry versions and deletion tombstones, use transactions for compare-and-set, and retain a device-local baseline. Independent local and remote edits stop as conflicts rather than choosing a winner. Authentication passwords are transient and Firebase persists only its own session. `applicationIdentity.ts` sets RimLib's display name and pins default Electron data/session paths to the `RimLib` storage directory before logging, instance locking or database loading. Explicit path overrides remain untouched. Only the configured location is used; identity setup never scans, migrates or merges other application folders. Identity setup failures show a native error and terminate before database access. The browser preview uses only the `rimlib:vault` and `rimlib:vault:backup` keys, without aliases or namespace migration. `VaultStore` serializes writes, rejects stale revisions/external edits, writes atomically, retains a previous-version backup and checkpoints destructive operations. Database loads and saves validate every known field before normalizing optional metadata. Unknown fields are passed through as opaque extensions. Explicit older or newer schema versions are rejected before backup recovery; the standalone `scripts/migrate-vault-v2-to-v3.mjs` tool performs the deliberate, backed-up v2 upgrade.

[Zod](https://zod.dev/api) validates external data at three boundaries. `shared/vaultValidation.ts` defines reusable mod/settings schemas and the stored v3 contract; it validates the header before the complete vault so unsupported versions cannot fall back to a backup. Open records preserve extension fields without coercion or schema defaults. The validated source is retained because Zod's parsed clone omits `__proto__`; pending-subscription checks examine every own entry rather than silently skipping that key. `shared/ipc.ts` defines an exhaustive channel-to-tuple schema map, rejecting wrong types, missing required arguments, unknown channels and extra arguments before actions. Save requests validate normalized runtime state and accept only supported save options. `main/workshopMetadata.ts` validates public HTTP request IDs and response envelopes; one shared normalizer strictly checks item/result/app identity and sanitizes optional metadata for both individual refresh and bulk import. Internal transformations and native subscription guards remain explicit domain logic, not schema side effects.

An ordinary save merges rather than replacing omitted records. Synchronization adds/enriches records and updates status, never deleting records. Explicit library deletion validates the entire selection and authoritative active state before checkpointing, then validates the selection again inside the serialized update. Direct deletion protects subscribed, active and unverifiable records; the compound draft path unsubscribes first, reloads the vault and only then invokes deletion. Approved deletions remove the saved records completely; the checkpoint, not an application-visible metadata archive, provides recovery.

Installed-folder status, actual Steam subscription IDs and the game's enabled packages are different observations. Folder scans are for metadata/presentation/import, the Steam SDK is for subscription actions, and `ModsConfig.xml` determines the active partition and order. Installed metadata enriches Core, DLC, local and Workshop rows but is not the authority for activation. A shared linear-time reconciler applies local Steam observations in both processes, preserves unknown state extensions, keeps unchanged object identities and updates only mod flags whose effective membership changed. Do not collapse these observations into one boolean or infer reliable active identity from cached package metadata.

The renderer loads active state progressively through separate read-only IPC boundaries. A configuration-only read publishes package IDs and game version first, allowing the active panel to render saved rows or placeholders without waiting for disk inventory work. A direct installed-inventory read then supplies local `About.xml` metadata, official artwork and sorting rules. Late enrichment merges metadata only and cannot restore an older package order; a request generation also prevents results from a previous configuration or Workshop path from leaking into the current view. Configuration loading, metadata loading and explicit refreshes have separate compact renderer states, so rows already backed by `ModsConfig.xml` remain visible and usable while enrichment continues. Cold startup still requires one read and schema validation of the local vault before its records can be trusted. Optional Firebase code is dynamically loaded only when sync is enabled, and Steam process availability is queried only at Apply time for drafts containing subscription work.

`InstalledModIndex` keys its cache by the effective Steam-library and Workshop-path inputs. Callers for the same key share one in-flight scan, and the settled inventory is reused instead of repeatedly parsing every `About.xml`. A scan from an obsolete key cannot replace the current official-preview approval map. After initialization, active configuration and Workshop-folder observations are refreshed only by explicit workflows: Workshop synchronization refreshes both and requests a forced installed-inventory scan, settings changes initialize the selected paths, and applying a draft verifies its resulting active configuration. If an older inventory scan is still running, one shared follow-up scan is queued so pre-sync results cannot satisfy the refresh. Activation/deactivation needs only a readable active configuration and remains available during enrichment. Auto-sort stays disabled until the installed identity/rule data needed to construct a proposal is available. Subscription and removal draft controls do not treat cached metadata, folder availability or Steam availability as authorization or as staging gates; full reads in main-process confirmation workflows establish safety immediately before execution.

Official content is recognized only through the exact shared Core/Royalty/Ideology/Biotech/Anomaly/Odyssey package registry. The installed-mod scanner resolves each recognized package's own `About/Preview.png` and registers only those scanner-approved paths. The renderer receives an internal image URL with no filesystem path; the main-process protocol accepts only a known package identity and never exposes generic `file:` access. Missing or unreadable official metadata/artwork is logged and degrades to the ordinary image fallback without hiding other installed entries.

Workshop synchronization treats incomplete enrichment as a first-class partial result. A requested item omitted from Steam's response, an invalid remote item, an unreadable `About.xml` or an installed item without a usable package ID adds a deduplicated warning and a structured `WARN` record with the affected Workshop ID. Successful local data and previously saved fields are preserved. `useWorkshopActions` shows those warnings separately from fatal action failures and keeps the compact header notice bounded; full details remain in the application log.

Every native unsubscribe funnels through a final active/readability/game-state guard immediately before the Steam call. Draft execution uses explicit whole-group native preflight and then guarded, identity-bound single-mod calls. Confirmed library deletion independently rejects active or unverifiable targets before creating a checkpoint. These are confirmation-time checks: staging a draft is not authorization, and preflight itself is a read/check operation rather than an authorization token. Confirmed Steam changes are recorded before reporting failures. The dedicated `setActiveMods` application API is the only configuration writer; it accepts both desired and expected orders and returns the freshly read active state. No application API downloads Workshop content.

The application models saved mods, tags, subscription observations, the external active configuration and device-local pending drafts. One derived known-mod universe combines saved records, installed metadata and placeholders for configured packages; its partition is exclusively active versus inactive. Successful filesystem discovery checkpoints installed non-official rows and scanner-owned update metadata, so the same discovery does not reappear as new after every launch. Subscribed items that have not been discovered or synchronized still cannot edit tags or refresh saved metadata until imported. There is no separate persisted modlist, deleted-mod archive or SteamCMD model. Existing unknown database fields remain opaque and are never used as action targets or reinterpreted as tags.

Read-only operations have deadlines and stale-response guards. Persistence writes are awaited, not abandoned by timers. Renderer actions report failures through notifications, and panel error boundaries do not recreate or empty the vault. Window closing is coordinated as an explicit save handshake: healthy renderers may finish without a deadline, save failures keep the window open for retry, and a renderer proven unavailable cannot leave application quit waiting forever.

## Readability Review

The main complexity was workflow ownership, not formatting. `App.tsx` combined tag creation, manager/editor return flags, bulk assignment, Steam availability checks, active projections, previews, progress and panel composition. Those workflows now have explicit owners, and shared panel props remove duplicated action wiring. Subscription, activity, ordering and deletion confirmation use one draft review; the superseded standalone dialogs and styles are removed.

`services/draftActions.ts` owns sequential draft execution, progress and failure retention. `SteamOperations` owns native preflight and individual guarded subscription mutations, while `rimWorldConfig.ts` exclusively owns the compared configuration write. There is no second token-based batch executor or persisted-selection action path. Every unsubscribe passes through `changeSubscription`'s final guard. Tag assignments use the selection-aware transformation for both single and multiple mods.

`steamWorkshop.ts` contains several filesystem/parsing stages, but the stages are named and tested. Concurrent callers share one in-flight raw discovery for the same effective path even if an individual caller times out, and installed metadata reads use an ordered bounded worker pool. `VaultStore` and `useModVault` are deliberately kept together: their write ordering, revision checks and locks are easier to audit as one lifecycle than as scattered generic helpers. Declarative CSS and test fixtures are not split solely to meet a line limit.

## Verification And Next Steps

The suite covers pure transformations, temporary filesystem stores, corruption/backup recovery, guarded active-configuration writes, About.xml rule parsing, sorter warnings/failures, races and partial subscription failures, request validation, SSR/control handlers, lint policy and staged commit isolation. Some layout assertions still inspect CSS/source; a few now use TypeScript ASTs so formatting cannot change their meaning.

Fast-check supplements example regressions with bounded generated vaults and independent action-sequence models. It checks current record preservation and explicit deletion, tags, selection, active/inactive projection, unavailable-drive status, native unsubscribe guards, public metadata refresh, IPC validation, log privacy and presentation geometry. Example tests cover graph ordering, deterministic ties, missing targets, cycles/duplicates, Core preservation, stale baselines and backup-before-write. Filesystem and HTTP/native tests use temporary stores and injected doubles; no real user database, Steam account or game config is accessed. This does not replace Electron rendering/focus tests. See [TESTING.md](TESTING.md) for run and replay policies.

The Playwright harness in `tests/e2e` launches the production main-process lifecycle, IPC validation/handlers, preload and renderer, retaining the real vault store, XML readers, installed-metadata index and Steam operation coordinator. A test-only esbuild entry substitutes native availability/Steam calls and discovery of the user's Steam/game directories. OS dialogs/shell actions and public metadata requests are controlled doubles. Production modules contain no test-mode environment branches or generic IPC escape hatch.

Each test owns a token-marked temporary directory for its database, backups, logs, session, Workshop content and game config. The launcher refuses missing/mismatched ownership and out-of-fixture paths, including symlink escapes. External HTTP requests are blocked; subscription changes and OS actions are recorded, never executed. Fixtures await shutdown before removing files. The build is separate from development output. These tests cover application interactions, not native SDK compatibility, OS permission dialogs or packaged upgrades.

The next architectural work should be driven by specific workflows and regression tests:

1. Extend the isolated Electron suite when workflows change, especially activation/deactivation, sort warning/failure notices, confirmation/recheck races and shutdown. Keep live Steam and packaged-binary validation explicit, authorized and separate from automated fixture tests.
2. Keep App focused on panel composition. Extract remaining derived views or file-action workflows only when their behavior grows; keep the vault's save/operation lock centralized and avoid competing state stores.
3. Add packaging/update tests and a dependency security review before distributing a public binary. ESM preload/native SDK constraints must be considered before changing Electron's sandbox settings.

Avoid changing the storage engine, rewriting the whole app or removing historical data merely to make the tree look cleaner. Database preservation and observable behavior take precedence over architectural symmetry.
